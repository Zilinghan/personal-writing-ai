    Part 1

    The ideas underneath

    01

    Computers, apps and containers

    20 min

    Before Kubernetes makes sense, you need three ideas: a server, a cluster and a container.

    From one computer to many

    A server is just a computer that runs programs for other people, usually sitting in a data center with no screen. When you use “the cloud” (like AWS), you're renting servers from someone else.

    One server can only handle so much. Big websites and AI training jobs need many servers working together. A group of servers working as one team is called a cluster. In Kubernetes, each server in the cluster is called a node.

    The problem containers solve

    Every app needs other software to run: a specific Python version, some libraries, system tools. Put two apps on one computer and their needs can clash. App A needs Python 3.8; App B needs Python 3.12. You can't easily have both as “the” Python.

    A container fixes this. It packs an app together with everything it needs into one sealed box. Each box has its own private copy of its tools, so boxes can't step on each other. Many containers can share one computer safely.

    Analogy

    Think of real shipping containers. Before them, every cargo ship was loaded by hand with sacks and barrels of every shape. Standard containers made any cargo fit any ship, crane or truck. Software containers do the same for apps: any app, packed the same way, runs on any machine.

    Image vs. container

    Two words you'll see constantly:

    • An image is the packed, frozen box sitting on a shelf. It's a file. Nothing is running.
    • A container is an image that has been started and is running.

    You can start many containers from one image, the way you can cook many identical dishes from one recipe.

    02

    What Kubernetes does, in one idea

    15 min

    Containers solved packing. They didn't solve managing. Picture 200 containers spread across 20 computers. Someone has to keep answering:

    • Which computer has room for this new container?
    • A container crashed at 3 a.m. Who restarts it?
    • A whole computer died. Who moves its containers somewhere else?
    • Traffic tripled. Who starts more copies, and who removes them later?
    • How do apps find each other when they keep moving between computers?

    Kubernetes (often written K8s, because there are 8 letters between K and s) is software that answers all of these for you, automatically. The name is Greek for “helmsman”, the person who steers a ship. Google built it from its own internal tools and gave it away in 2014.

    The big idea: you describe the goal, it keeps it true

    You don't give Kubernetes step-by-step orders. You give it a description of how things should look, like “keep 3 copies of my web app running”. Kubernetes then checks, over and over, whether reality matches. If not, it fixes the difference.

    Remember

    You tell Kubernetes what you want, not how to do it. It keeps comparing “what you want” with “what is” and closes the gap, forever.

    This one idea explains a lot:

    • It heals itself. Delete one of the 3 copies by hand, and Kubernetes sees only 2 and starts a new one.
    • Changes take a few seconds. When you submit a change, Kubernetes accepts it right away, then works toward it. You watch it happen.
    • Your setup lives in text files. The “description” is a short text file (in a format called YAML). You can save it, share it, and recreate the same setup anywhere.

    What it can do for you

    JobIn plain words
    Placing workFinds a computer with enough free CPU, memory or GPU for each container.
    Self-healingRestarts crashed containers; moves work off broken computers.
    Finding each otherGives each app a fixed name other apps can call, even as containers move.
    Safe updatesReplaces old versions with new ones a few at a time, and can undo.
    ScalingAdds copies when busy, removes them when quiet. Can even add computers.
    Settings & passwordsHands configuration to apps without baking it into the image.
    StorageAttaches disks that keep data even when containers restart.
    Add-onsCan be extended to manage new kinds of things, such as Ray clusters for AI work.

    Part 2

    The parts of Kubernetes

    03

    The 8 words to know

    20 min

    Almost everything in Kubernetes uses these eight words. Learn them first, and the rest of the guide will read easily. Start with the picture: things fit inside each other like boxes.

    Cluster

    All the computers Kubernetes manages, treated as one big computer.

    Like: a whole restaurant.

    Node

    One computer in the cluster. It can be a real machine or a rented cloud server.

    Like: one cooking station in the kitchen.

    Container

    A running app, sealed with everything it needs (chapter 1).

    Like: one dish being cooked.

    Pod

    The smallest thing Kubernetes runs: one or a few containers that always live together on the same node and share one network address.

    Like: one plate. Usually one dish, sometimes a main plus a side.

    Deployment

    Your instruction “keep N copies of this pod running”. It handles replacing and updating pods.

    Like: a standing order: “always have 3 plates of soup ready”.

    Service

    A fixed name and address that sends traffic to the right pods, even as pods come and go.

    Like: the restaurant's phone number, which stays the same whoever answers.

    Namespace

    A labeled folder inside the cluster that keeps one team's or project's things apart from another's.

    Like: separate sections of the menu.

    Control plane

    The “brain” of Kubernetes: the programs that store your goals and make decisions. Chapter 4 opens it up.

    Like: the restaurant's manager and order desk.

    Two more ideas that show up everywhere

    Pods are temporary. Kubernetes freely deletes and recreates pods: when updating, when a node fails, when scaling down. Each new pod gets a new name and a new network address. Never rely on a particular pod sticking around. That's why Deployments (to recreate them) and Services (to find them) exist.

    Labels connect things. A label is a sticky note on an object, like app=web. Kubernetes objects find each other by label, not by name. A Deployment says “the pods with sticker app=web are mine”. A Service says “send traffic to pods with sticker app=web”. Chapter 5 shows this in a picture.

    04

    Who does what inside Kubernetes

    20 min

    Kubernetes isn't one program. It's a handful of small programs, each with one job. They split into two groups:

    • The control plane (the brain) stores what you want and decides what should happen. It usually runs on its own computers. With cloud versions like Amazon EKS, the cloud company runs it for you and you never see those computers.
    • The worker nodes (the muscle) actually run your containers.

    Follow one request from start to finish

    Say you ask for 3 copies of a web app. Here's who does what. Notice how each part does its small job and the next part picks up from there.

    Remember

    Kubernetes is a notebook (etcd) with a front desk (API server) and a crew of helpers who each watch for one kind of change and do one job. When something gets stuck, ask: “which helper should have acted next, and why didn't it?”

    05

    Writing down what you want

    25 min

    You describe what you want in short text files written in YAML, a simple format of name: value lines where indentation shows what belongs to what. Each file describes one or more objects (a Deployment, a Service, and so on). Every object has the same four parts:

    apiVersion: apps/v1     # which version of the rules this follows (copy it from examples)
kind: Deployment        # what kind of thing this is
metadata:               # its name, and its labels (sticky notes)
  name: web
spec:                   # "spec" = specification: what you WANT
  ...
# Kubernetes adds a "status" part itself: what IS actually happening

    A Deployment, explained line by line

    This is the file you'll write most often. It says “run 3 copies of my web app”.

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: web                     # call this Deployment "web"
spec:
  replicas: 3                   # keep 3 copies running at all times
  selector:
    matchLabels:
      app: web                  # "pods with the sticker app=web are mine"
  template:                     # the blueprint for each pod
    metadata:
      labels:
        app: web                # put the sticker app=web on each new pod
    spec:
      containers:
      - name: web
        image: nginx:1.27       # which image to run (a free web server)
        ports:
        - containerPort: 80     # the app listens on port 80 (see chapter 7)
        resources:
          requests:             # how much of a computer this needs
            cpu: 250m           # a quarter of one CPU core
            memory: 128Mi       # 128 megabytes of memory

    How objects find each other: labels

    A Deployment doesn't control pods directly. It creates a helper called a ReplicaSet, whose only job is keeping the count right, and that helper makes the pods. Every pod gets the sticker app=web. A Service (chapter 9) later finds the same pods by looking for that sticker.

    Other kinds of workload

    Deployments are for apps where every copy is the same and any copy can be replaced. Some jobs need something different:

    KindUse it whenExample
    DeploymentCopies are interchangeableWebsites, APIs
    StatefulSetEach copy needs its own fixed name and its own diskDatabases. Copies are named db-0, db-1, db-2 and keep those names forever.
    DaemonSetYou need exactly one copy on every nodeA program that collects logs from each computer
    JobWork that runs once and finishesProcess a batch of files, train a model
    CronJobA Job on a timetableNightly backup at 2 a.m.

    Settings and passwords

    You don't want settings baked into the image, or you'd have to rebuild it for every change. Kubernetes keeps them separately and hands them to the pod when it starts:

    • A ConfigMap holds ordinary settings, like LOG_LEVEL=info.
    • A Secret holds sensitive ones, like passwords. (By default it is only lightly scrambled, not truly encrypted, so access to Secrets should be limited.)

    Keeping data: storage

    Anything a container writes to its own files is lost when it restarts. To keep data (a database, model checkpoints), you attach a disk. Kubernetes splits this in two so app writers don't need to know the details of the cloud:

    Try it 
    kubectl create deployment web --image=nginx:1.27 --replicas=3   # make a Deployment
kubectl get pods                    # see 3 pods with random-looking names
kubectl get pods --show-labels      # see their app=web stickers
kubectl delete pod <one-pod-name>   # delete one...
kubectl get pods                    # ...and a new one has already replaced it
    06

    Updates, self-healing and scaling

    20 min

    Updating without downtime

    When you change the image from version 1 to version 2, Kubernetes doesn't stop everything and restart. It does a rolling update: start one new copy, wait until it's healthy, remove one old copy, repeat. Users are served the whole time.

    Health checks

    How does Kubernetes know a copy is “healthy”? You tell it how to check, usually “ask this web address and expect an OK”. There are two main checks:

    • Readiness check: “Can this copy take customers right now?” If it fails, Kubernetes stops sending it traffic but leaves it running. Used while an app is warming up.
    • Liveness check: “Is this copy stuck?” If it fails, Kubernetes restarts the container.

    Self-healing

    How much room does a pod need?

    Each pod says how much CPU and memory it needs (the requests in chapter 5). The scheduler adds these up and only places a pod on a node that still has enough room. If no node has room, the pod waits in a state called Pending.

    There are also limits: a ceiling a pod can't go above. Go over the memory limit and the container is killed and restarted (you'll see OOMKilled, short for “out of memory”). Go over the CPU limit and it's just slowed down.

    Growing and shrinking automatically

    Go deeper: steering pods to particular nodes (optional)

    Sometimes a pod must run on a certain kind of node, for example a GPU node for AI training. A few tools control this:

    • nodeSelector: “only run on nodes with this label”, e.g. gpu=true.
    • Taints and tolerations: a node can put up a “keep out” sign (taint). Only pods carrying a matching pass (toleration) may land there. Used to keep ordinary pods off expensive GPU nodes.
    • Affinity / anti-affinity: “run near” or “run away from” other pods, e.g. spread copies across nodes so one failure can't take them all out.

    Part 3

    How network traffic moves

    07

    Networking basics you need first

    20 min

    Kubernetes networking is built on everyday internet ideas. Four of them are enough: IP address, port, DNS and load balancer.

    IP address, port and DNS

    • An IP address is a computer's street address on a network, like 10.0.0.5. To send anything to a computer, you need its address.
    • A port is a numbered door on that computer. One computer can run several programs, each listening at its own door. Web servers usually use door 80 (or 443 for secure https); a PostgreSQL database uses 5432.
    • DNS is the internet's phone book. People remember names like shop.example.com; DNS turns them into IP addresses.

    Private addresses and translation (NAT)

    Most addresses inside a company or cloud network are private (they start with 10., 172.16–31. or 192.168.). They work inside that network but mean nothing on the public internet. Your home Wi-Fi works the same way: your laptop has a private address, and your router swaps in the home's single public address on the way out. That swapping is called NAT (network address translation). Keep it in mind; Kubernetes uses address swapping in a clever way in chapter 9.

    Load balancer

    A load balancer is a traffic splitter. Clients connect to one address; the load balancer passes each connection on to one of several identical servers behind it, so no single server gets overwhelmed and a broken one can be skipped.

    08

    How pods talk to each other

    20 min

    Kubernetes has one simple promise about networking. Everything else is built on it.

    The promise

    Every pod gets its own IP address. Any pod can reach any other pod directly at that address, even when they're on different nodes, with no address swapping in between.

    In practice: each node is handed a block of addresses for its pods. Node 1 might hand out 10.244.1.x, node 2 10.244.2.x. When a pod starts, it gets the next free address from its node's block.

    Containers inside the same pod share one address. They talk to each other over localhost (“this same computer”), like two programs on your laptop.

    Who builds this network?

    Kubernetes states the promise but doesn't build the network itself. A plug-in called a CNI plugin (Container Network Interface) does. You pick one when the cluster is set up. Common ones: AWS VPC CNI (the default on Amazon EKS, gives pods real AWS network addresses), Calico, Cilium and Flannel. They all keep the same promise; they differ in speed and extra features.

    Getting pod traffic from node 1 to node 2 works one of two ways:

    Go deeper: the Linux plumbing inside a node (optional)

    Each pod gets its own network namespace: a private copy of the computer's network settings, so pods can't see each other's network cards. A veth pair is a virtual cable: one end appears inside the pod as eth0, the other end sits on the node. The node's routing table then says which addresses live where.

    When a pod is created, the container runtime calls the CNI plugin with the command “ADD”. The plugin makes the virtual cable, picks an address from the node's block, and sets the routes. When the pod is deleted, it's called with “DEL” to clean up.

    Try it 
    kubectl run a --image=nicolaka/netshoot -- sleep infinity    # a pod full of network tools
kubectl get pods -o wide            # the IP column shows each pod's own address
kubectl exec a -- ip addr           # look inside pod a: its eth0 and address
kubectl exec a -- curl -s <IP of a web pod>    # talk to another pod directly
    09

    Services: a stable name for changing pods

    20 min

    Pod addresses work, but they have a problem: pods are temporary (chapter 3). Every time a pod is replaced, it gets a new address. And there are usually several copies. How is the front-end supposed to know where the API pods are right now?

    apiVersion: v1
kind: Service
metadata:
  name: api               # other apps will call this name
spec:
  selector:
    app: api              # send traffic to pods with sticker app=api
  ports:
  - port: 80              # the door callers knock on
    targetPort: 8080      # the door the app inside the pod actually uses

    Who can reach a Service: the three main types

    Each Service gets a fixed private address called its ClusterIP. The type setting decides how far beyond the cluster it can be reached:

    TypeReachable fromUse it for
    ClusterIP (default)Only inside the clusterApps talking to each other: front-end → API → database
    NodePortAny node's address, on a door between 30000 and 32767Testing; rarely used directly
    LoadBalancerOutside, via a cloud load balancerExposing one service to the internet or to your company network

    The cluster's own phone book

    Kubernetes runs its own DNS, called CoreDNS. Every Service automatically gets a name in it. Inside the cluster, a pod can just call http://api. The full name is api.<namespace>.svc.cluster.local, which you only need when calling a Service in a different namespace (folder). For example, api.shop reaches the api Service in the shop namespace.

    What really happens when a pod calls a Service

    Here's the surprising part: there's no actual load-balancer program sitting at the Service's address. Instead, every node gets traffic rules that quietly swap the Service address for a real pod address as the request leaves. This is the address swapping (NAT) from chapter 7.

    Common mistake

    If a Service “doesn't work”, check whether it found any pods: kubectl get endpointslices (the official name for the “list of healthy pods”). An empty list almost always means the sticker (label) in the Service doesn't match the pods, or the pods are failing their readiness check.

    Go deeper: the actual rules, and two classic surprises (optional)

    On Linux, kube-proxy writes these rules using a built-in kernel firewall called iptables (newer clusters use its successor, nftables; the plug-in Cilium uses a faster technology called eBPF instead). For a Service with 3 pods, the rules look roughly like this:

    # traffic to the Service address, door 80 → go to the "web" rule list
-A KUBE-SERVICES -d 10.96.12.34 -p tcp --dport 80 -j KUBE-SVC-WEB
# pick pod A one time in three; otherwise pod B half the time; else pod C
-A KUBE-SVC-WEB -m statistic --mode random --probability 0.333 -j POD-A
-A KUBE-SVC-WEB -m statistic --mode random --probability 0.500 -j POD-B
-A KUBE-SVC-WEB -j POD-C
# rewrite the destination to the real pod address
-A POD-A -p tcp -j DNAT --to-destination 10.244.1.8:8080

    The kernel remembers the choice for the whole connection (a feature called conntrack), so replies find their way back.

    Surprise 1: one busy pod. The choice is made once per connection, not per request. Some protocols (like gRPC) open one connection and send thousands of requests over it, so all of them land on the same pod. Fixes include smarter clients or a service mesh (chapter 10).

    Surprise 2: slow lookups for outside names. To make short names like web work, each pod's DNS settings try adding cluster suffixes first. A lookup for api.stripe.com is first tried as api.stripe.com.shop.svc.cluster.local, then a couple of other variations, before the real name. Each extra attempt adds a little delay. Writing the name with a final dot (api.stripe.com.) skips the guessing.

    Try it 
    kubectl expose deployment web --port=80            # make a Service for the web pods
kubectl get service web                             # note its CLUSTER-IP
kubectl get endpointslices                          # the list of pod addresses it found
kubectl exec a -- curl -s http://web | head -n 4    # call it by name from pod a
    10

    Letting the world in, and keeping the wrong traffic out

    20 min

    One front door for many websites: Ingress and Gateway

    A LoadBalancer Service per app works, but each one costs money and only forwards raw connections. For websites, you usually want one public entry point that reads the web address and sends each request to the right app. It also handles the padlock (HTTPS security certificates) in one place.

    Kubernetes has two ways to describe that front door. The older one is Ingress. The newer, more capable one is Gateway API. Both work the same way in principle:

    Writing the rules down isn't enough by itself: the cluster also needs a controller, a program that reads your rules and does the routing. Examples are the AWS Load Balancer Controller on EKS, Envoy Gateway, or Traefik. For new setups, prefer Gateway API; the most popular older Ingress controller, ingress-nginx, has been retired by the Kubernetes project.

    # A Gateway API route, in plain words: "for shop.example.com/api, send 90% to v1 and 10% to v2"
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: api }
spec:
  parentRefs: [{ name: public-gateway }]     # attach to the shared front door
  hostnames: [shop.example.com]
  rules:
  - matches: [{ path: { type: PathPrefix, value: /api } }]
    backendRefs:
    - { name: api-v1, port: 80, weight: 90 }   # most traffic to the old version
    - { name: api-v2, port: 80, weight: 10 }   # a little to the new one, to test it

    Keeping the wrong traffic out: NetworkPolicy

    By default, any pod can talk to any other pod. That's convenient but risky: if a hacker breaks into the front-end, they can reach the database directly. A NetworkPolicy is a firewall rule for pods: “only pods with sticker X may talk to pods with sticker Y on door Z.”

    apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: db-only-from-api }
spec:
  podSelector:
    matchLabels: { app: database }    # this rule protects the database pods
  ingress:                            # "ingress" here means incoming traffic
  - from:
    - podSelector:
        matchLabels: { app: api }     # only api pods may come in
    ports:
    - port: 5432                      # and only to the database door
    Common mistake

    NetworkPolicy only works if the cluster's network plug-in (chapter 8) supports it. Calico and Cilium do. Some simple setups (Flannel alone, or a default practice cluster) quietly ignore the rules. Also, if you block outgoing traffic, remember to still allow DNS (door 53), or no pod can look up any name.

    Go deeper: service mesh, and who sees the real visitor address (optional)

    A service mesh (Istio, Linkerd) adds a small helper proxy next to every app. All traffic between apps goes through these helpers, which add encryption between pods, automatic retries, and detailed traffic graphs, without changing app code. It's powerful but adds a lot to run. Most teams don't need one at first.

    Visitor addresses. When traffic arrives from a load balancer, a node may forward it to a pod on another node, swapping in its own address on the way. Then your app sees the node's address, not the visitor's. Setting externalTrafficPolicy: Local on the Service keeps the real visitor address. Web gateways usually pass it along in a header called X-Forwarded-For instead.

    Pods reaching the internet. When a pod calls something outside the cluster, its node usually swaps in the node's own address (NAT), because the outside world doesn't know pod addresses. On AWS, private nodes then go out through a “NAT gateway”, which charges per gigabyte, a common source of surprise bills.

    Networking cheat sheet

    I want to…Use
    Let two containers in one pod talklocalhost
    Give a group of pods one stable nameA Service (type ClusterIP)
    Put one non-web service on the internetA Service of type LoadBalancer

    Part 4

    Using it for real

    11

    Should you use Kubernetes?

    10 min

    Kubernetes is powerful but has real running costs: upgrades a few times a year, and someone who understands it when things break. For small projects, simpler services do the job with far less effort.

    Kubernetes is a good fit when you have many services or several teams, traffic that rises and falls, or a mix of web apps, batch jobs and GPU work sharing the same machines. That last case is why it's popular for AI and research computing.

    Example: Ray on Kubernetes

    Kubernetes can be taught new kinds of objects. Add-ons that do this are called operators. KubeRay is the operator for Ray: you write a short file saying “a Ray head plus 0–8 GPU workers”, and it creates and removes the pods for you. Paired with a node autoscaler, GPU machines are rented only while workers need them and released afterwards, so idle GPUs stop costing money.

    12

    Your first hands-on session

    10 min

    You control Kubernetes with a command-line tool called kubectl (say “cube control”). It reads a settings file on your laptop (~/.kube/config) that says which cluster to talk to and proves who you are. Then it sends your requests to the API server.

    The commands you'll use 90% of the time

    # LOOK
kubectl get pods                 # list pods in the current namespace
kubectl get pods -A              # ...in all namespaces
kubectl get deploy,svc           # list Deployments and Services
kubectl describe pod <name>      # full details; the "Events" at the bottom explain problems
kubectl logs <pod-name>          # what the app printed
kubectl logs <pod-name> --previous   # what it printed before it last crashed

# CHANGE
kubectl apply -f web.yaml        # "make it look like this file" (create or update)
kubectl delete -f web.yaml       # remove what the file describes
kubectl scale deploy web --replicas=5
kubectl rollout undo deploy/web  # go back to the previous version

# GET INSIDE
kubectl exec -it <pod-name> -- sh       # open a shell inside a pod
kubectl port-forward svc/web 8080:80    # reach a Service at localhost:8080

# LEARN (works offline)
kubectl explain deployment.spec  # built-in docs for any field

    A friendly extra tool is k9s, a full-screen terminal view of your cluster you can browse with arrow keys.

    How teams usually ship changes

    1. Build a new image of the app and upload it to a registry.
    2. Change the image version in the YAML file, and save that change in Git.
    3. A tool (a CI pipeline, or one called Argo CD that watches Git) runs kubectl apply for you.
    4. Kubernetes does a rolling update (chapter 6). If something looks wrong, undo.
    13

    When things break

    10 min

    The first command is always kubectl get pods, then kubectl describe pod <name> and read the Events at the bottom. The STATUS column tells you where to look:

    Status you seeWhat it meansWhat to do
    PendingWaiting for a node with enough room (chapter 6)Read Events: “Insufficient cpu” or similar. Ask for less, or add nodes.
    ImagePullBackOffCan't download the imageCheck the image name and version for typos; check registry login.
    CrashLoopBackOffThe app keeps starting and crashing; Kubernetes waits longer between each retrykubectl logs <pod> --previous shows the error.
    OOMKilledUsed more memory than its limitRaise the memory limit or fix the memory use.
    Running but 0/1 readyRunning, but failing its readiness check, so it gets no trafficCheck the health check's path and port.

    14

    What's the difference between an image and a container?

    An image is the frozen package on the shelf. A container is an image that's been started and is running. One image can start many containers.

    Put these in order from biggest to smallest: pod, cluster, container, node.

    Cluster → node → pod → container.

    You delete one of the 3 pods in a Deployment. What happens?

    The reconcile loop sees 2 instead of 3 and creates a new pod. It gets a new name and a new address.

    Which part decides which node a pod runs on? Which part actually starts it?

    The scheduler decides. The kubelet on that node starts it, using the container runtime.

    Why do we need Services if every pod has an address?

    Pod addresses change whenever pods are replaced, and there are usually several copies. A Service gives one fixed name and address and spreads traffic across whichever healthy pods exist right now.

    A Service exists but calling it fails. What's the first thing to check?

    Whether it found any pods: kubectl get endpointslices. If the list is empty, the label in the Service probably doesn't match the pods' labels, or the pods aren't passing their readiness check.

    Pod A on node 1 calls pod C on node 2 directly. Whose address does pod C see as the sender?

    Pod A's own address. Kubernetes promises pod-to-pod traffic without address swapping.

    What's the difference between ClusterIP and LoadBalancer?

    ClusterIP can only be reached from inside the cluster. LoadBalancer adds a cloud load balancer with an outside address, so people outside can reach it.

    You have five websites. Why use a Gateway instead of five LoadBalancer Services?

    One load balancer and one place for certificates, with rules that route by web address and path. It's cheaper and easier to manage.

    A pod shows CrashLoopBackOff. Which command shows you why?

    kubectl logs <pod> --previous shows what the app printed before its last crash.

    You wrote a NetworkPolicy and nothing changed. Why might that be?

    The cluster's network plug-in doesn't enforce NetworkPolicy (for example Flannel alone). The rule is saved but nobody acts on it.

    In one sentence, what is an operator such as KubeRay?

    An add-on that teaches Kubernetes a new kind of object (like a Ray cluster) and runs its own reconcile loop to keep it the way you described.

    Glossary in plain words

    reference
    API server
    The front desk of Kubernetes. Every request goes through it.
    CNI plugin
    The add-on that gives pods their network addresses and connects them.
    ClusterIP
    A Service's fixed private address, reachable only inside the cluster.
    Cluster
    All the computers Kubernetes manages, working as one.
    ConfigMap
    Stored settings handed to pods.
    Container
    A running app sealed with everything it needs.
    Control plane
    The brain: API server, etcd, scheduler, controllers.
    Controller
    A helper that keeps one kind of thing matching what you asked for.
    CoreDNS
    The cluster's own phone book for Service names.
    DaemonSet
    “Run one copy on every node.”
    Deployment
    “Keep N identical copies running, and update them safely.”
    DNS
    The phone book that turns names into IP addresses.
    EndpointSlice
    The list of healthy pod addresses behind a Service.
    etcd
    The reliable notebook where Kubernetes stores everything.
    Gateway / Ingress
    The front door that routes web requests to Services by address and path.
    Image
    The frozen package a container is started from.
    IP address
    A computer's (or pod's) address on a network.
    Job
    Work that runs once to completion.
    kube-proxy
    Writes the traffic rules on each node that make Services work.
    kubectl
    The command-line tool you use to talk to Kubernetes.
    kubelet
    The helper on each node that starts and watches its pods.
    Label
    A sticky note like app=web that other objects use to find things.
    Load balancer
    Spreads incoming connections across several servers.
    Namespace
    A folder inside the cluster to keep teams or projects apart.
    NAT
    Swapping one address for another as traffic passes through.
    NetworkPolicy
    A firewall rule saying which pods may talk to which.
    Node
    One computer in the cluster.
    Operator
    An add-on that teaches Kubernetes to manage a new kind of thing.
    Pod
    One or a few containers that live together and share an address.
    Port
    A numbered door on a computer where a program listens.
    Readiness check
    “Can this pod take traffic yet?” Failing means no traffic, no restart.
    Liveness check
    “Is this pod stuck?” Failing means restart.
    Scheduler
    Decides which node each new pod runs on.
    Secret
    Stored sensitive settings such as passwords.
    Service
    A fixed name and address in front of a changing group of pods.
    StatefulSet
    Like a Deployment, but each copy keeps a fixed name and its own disk.
    YAML
    The simple text format Kubernetes files are written in.
